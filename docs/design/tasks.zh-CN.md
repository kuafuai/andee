# 设计草案：事 —— 接下的事办完为止，认识的人只记一次

状态：草案，未实现 · 适用：Android 与 Mac 两个身体，仅本机大脑 · 2026-11-09

关联：`inner-drive.zh-CN.md`（自己、在意、人）、`proactive-nudge.zh-CN.md`（气泡与计划）

## 0. 一句话

Andee 接下一件事，常常一轮办不完：要先问别人、要等回信、要过一会儿再看。现在这一轮一结束，这件事就只剩上下文里的一段文字。中间隔几件别的事，它就忘了，或者记岔了。

这份设计加一个通用的「事」（Task），让一件事从接下到交付都由设备记着。顺带把「人」做成一个人只记一条，并且说过话的人一定有记录。

## 1. 现在的问题

**1.1 一个真实的失败**

A 在 B 群问了 Andee 一个问题。它不知道怎么答，就去 C 群问 leader，这一轮随即结束。leader 回复时，中间已经隔了别的事。结果 Andee 要么没接上，要么回到 B 群 @ 了另一个人。

拆开看是三处断点：
- 通知 triage 是一次不带上下文的调用（`NotificationTriage.decide`），不知道 leader 那条消息是它在等的回答，可能判成 `ignore`。
- 就算判成 `act`，新回合也只剩那条通知，不知道这个回答是给谁的。
- 回到 B 群时，"是谁问的"只能凭记忆里的名字去找。群昵称、备注名、微信名对不上时，就会 @ 错人。

**1.2 "欠着的事"散在四处**

| 现有 | 实际是 | 缺什么 |
|---|---|---|
| `Todo` | 定时唤醒（once / cron） | 没有来源，没有在等谁，到点跑一次就完 |
| `cares` 的 `promise` | 有截止时间的牵挂 | 最多 7 条，没有来源，没有交付对象 |
| `People.Owed` | 挂在人身上的欠账（i_owe / they_owe） | 没有会话锚点，不会唤醒它 |
| `LocalBrain.Unfinished` | 被步数上限截断的那一轮 | 只活一小时，只管"继续" |

谁都不完整，同一件事又能记在两三个地方。

**1.3 「人」会漏记，也会重复**
- 建档全靠模型想起来调 `person upsert`。忙着办事时它想不起来。
- `People.unconfirmed()`（设备自动建档）写好了，但一个调用方都没有。
- 每条用户消息带着自己、维基、计划的索引行，唯独没有人。
- `upsert` 不带 channel 时不查重，直接新建。微信没有稳定 ID，同一个人在群里和私聊里名字不同，就成了两条。

## 2. 原则

1. **判断交给模型，事实由设备记。**接不接一件事、走哪个渠道去问、怎么回、什么时候放弃，都是模型的判断。来源是谁、从哪个会话来、信任级别是什么、等的人有没有说话，这些是事实，由设备记录和匹配，不让模型手抄。
2. **闹钟是闹钟，事是事。**`Todo` 只管"几点叫醒我"；事管"这件事办到哪了"。事需要定时回来看时，生成一个指向它的 todo。
3. **信任跟着事走。**从陌生人那里开始的事，由它引出的每一个回合都是 untrusted，和 `Todo.untrusted` 同一个理由：不能借一件事，把陌生人的话洗成一个 trusted 回合。
4. **人只记一条，合并要能撤销。**设备负责查出疑似重复，模型和用户都可以合并，合并留痕、可撤销。

## 3. 「事」

### 3.1 记录

存在笔记本分区 `tasks`，和其它分区一样加密存储，抹除和导出都覆盖。

| 字段 | 谁写 | 说明 |
|---|---|---|
| `id` | 设备 | `T` + 序号，索引里就用它 |
| `what` | 模型 | 一句话：这件事是什么 |
| `from` | **设备** | 来源锚点，见 3.2 |
| `deliver_to` | 设备给默认值，模型可改 | 办完交给谁。默认就是 `from` |
| `waiting_on` | 模型登记，设备补全 | 在等什么，可以有多个，见 3.3 |
| `next` | 模型 | 下一步做什么，一句话 |
| `steps` | 模型 | 几行进展记录，最多 20 行 |
| `due` | 模型，可选 | 截止时间 |
| `status` | 两者 | `open` / `waiting` / `ready` / `done` / `dropped` |
| `untrusted` | **设备** | 从来源继承，见 §5 |
| `created_at` / `touched_at` | 设备 | |

**事可以由任何来源开启**：你说的、你打字的、通知、朋友托付的、它自己起意的。

### 3.2 来源锚点（`from`）

每个回合开始时，设备记下这个回合的来源。`task open` 时自动带上，模型不需要也不能手填。

```
kind:    voice | typed | notify | friend | self | todo
app:     com.tencent.mm …            （notify）
chat:    会话名                       （notify：EXTRA_CONVERSATION_TITLE / Mac 的会话）
group:   true / false
sender:  发送者在这个会话里的显示名     （notify）
person:  对应的人的 id                 （设备匹配到就填，见 §4.3）
quote:   原话前 80 字
at:      时间
peer:    朋友设备 id                   （friend）
```

拿不到的字段就空着。比如 Mac 微信没开「显示消息详情」时，只有会话，没有发送者。空着要如实告诉模型，不让它猜。

**交付时用锚点，不用记忆。**处理一件事的回合，消息里附上完整的 `deliver_to`，并说明：回到那个会话，按原话找到那条消息，引用回复；找不到，再按锚点里的显示名 @。怎么回是模型的事，但"回给谁"以锚点为准。

### 3.3 在等什么（`waiting_on`）

两种：
- **等人**：`{person, app, chat, sender, asked, asked_at}`。模型调 `task wait` 时给出人和问了什么；app 和会话，设备从这一轮里实际发过消息的地方补上。补不上，就按模型给的。
- **等时间**：`{at}`。设备生成一个 `Todo`，带上 `task` 字段，到点唤醒时带着这件事。

### 3.4 工具：`task`（localOnly，`note.task`）

| action | 参数 | 说明 |
|---|---|---|
| `open` | what, next, due? | 来源和信任级别由设备从当前回合带上 |
| `wait` | id, on: person / at, asked | 登记在等谁或等什么时候，状态变成 `waiting` |
| `step` | id, text, next? | 记一步进展 |
| `done` | id, result | 办完了。由模型声明，但必须在本回合对 `deliver_to` 有过一次实际输出（发了消息，或者对你说了话），否则拒绝并说明原因 |
| `drop` | id, why | 放弃。原因会写进动态 |
| `list` / `get` | | 读 |

**接不接、走什么渠道、什么时候放弃，全部由模型判断。**一个陌生人在群里问的问题算不算接下一件事，邮件来的事是开邮件 app 回还是走别的路，设备都不插手。

### 3.5 什么会让它回到一件事

1. **等的人说话了。**通知进来时，设备在 triage 之前，用 `(app, chat, sender)` 去和所有 `waiting` 状态的事的 `waiting_on` 做匹配。命中了就把事标成 `ready`，并在 triage 的 system 消息里加一句："这是 T3 在等的回答"。triage 仍然是那次独立的调用，只是多知道一个事实。如果判 `act`，回合里会带上 T3 的完整记录。
   - 这条匹配也要走 triage 前面那几道免费的门（`offerForTriage` 的防抖、预算），不另开后门。
   - 正在跑别的回合时，按现有的 `held` 机制排队，不丢。
2. **到时间了。**由 3.3 生成的 todo 唤醒，带着 `task` 字段。
3. **朋友回报了。**`PeerTasks.Brain.answered` 按 peer 和请求 id 匹配到对应的事。
4. **你问起。**每条用户消息加一行「在办」索引：`在办：T3 A@B群 问报价 ← 等 leader@C群 2小时 · T5 订周六的票 next: 等放票`。最多列 5 件，按最近更新排序。和其它索引行放在同一位置，理由也一样：不能动缓存的前缀。
5. **心跳。**没办完的事像 care 一样参与逾期计算（`Heartbeat`）：有 due 的按截止时间算，没有的按 `touched_at` 算。等太久没进展，就会出现在心跳要处理的东西里。之后是去催、告诉你，还是放弃，由模型判断。

### 3.6 兜底：事要真的被建起来

只靠模型自觉是不够的，「人」已经证明了这一点。
- **prompt 规则**：这一轮办不完、要等别人或要稍后再做的事，结束前先 `task open`。
- **回合结束时检查**：这一轮对外发过消息（问了别人），却没有任何一件事处于 `waiting`，设备就在回合结束前给模型一次提醒，只提醒一次。要不要建，仍由模型决定。
- **复盘**：复盘规则加一条，检查今天交代过、或答应过却没有记成事的东西。

## 4. 「人」

### 4.1 按会话区分身份

`Channel` 加一个可选字段 `chat`：
- 私聊名：`(wechat, chat="", handle=名字)`
- 群昵称：`(wechat, chat="B群", handle=小王)`

同一个群昵称在不同群里可能是不同的人，所以按会话区分，不跨群通用。邮件地址、手机号这类全局唯一的 handle，`chat` 留空。

### 4.2 upsert 先查重

没带 `id` 时，设备先把名字归一化（去空格、去 emoji、小写），再按名字、别名、handle 查一遍：
- 有 channel 且完全命中：更新那一条（现有行为）。
- 疑似同一个人：**不新建**，返回 `possible_same: [{id, name, why}]`。模型要么带上 `id` 再写一次，要么传 `new: true` 表示确实是另一个人。
- 没有疑似：新建。

### 4.3 说过话的人由设备自动记录

**什么算说过话**：
- 私聊里给 Andee（或用户）发消息的人；
- 群里 @ 了 Andee、或引用了它消息的人；
- 任何一个回合的来源发送者。

只在群里发言、没和它说过话的人不记。

**怎么记**：设备在回合开始时，用来源锚点按 4.1 去匹配人。匹配上了，就把这个人的 id 写进锚点，再追加一条 `log in`。没匹配上，就调用 `unconfirmed()` 建一条未确认记录。整个过程不需要模型做任何事。

**triage 判成 `ignore` 的私聊发送者不建档**（广告、骚扰）。判成 `tell` / `act` 的才建，否则「人」会被垃圾填满。

**用户消息加一行「人」的索引**：只列和当前来源相关的人，比如来源发送者，以及他关联的进行中的事里等着的人。不列全部。

### 4.4 合并

`person merge(keep, drop, reason)`：
- 别名、channel、印象、往来记录合到 `keep`；见面时间取早的；用户编辑过的那条，以它的 relation 为准。
- `drop` 留一个 `merged_into` 指针，事和往来记录里引用的旧 id 都还能找到人。
- **owner 的记录不能被合并。**
- **untrusted 回合不能合并**（`TurnGuards`）。陌生人一句"我就是 X"不能换来别人的档案。
- 合并在动态里留一行（`BrainEvent`）；被合掉的那条快照保留 30 天，小本本 → 人 里可以撤销。
- 复盘时，设备列出疑似重复的几组交给复盘判断。合不合由模型决定。

用户在小本本 → 人 里也能手动合并。

## 5. 信任

- 事的 `untrusted` 等于开启它的那个回合的 untrusted。由它引出的每个回合（通知匹配、到点唤醒、心跳）都按这个级别运行。
- 一件 trusted 的事里，等到的回答来自一个陌生人的通知，**那个回合仍然是 untrusted**：回答的内容是陌生人写的。和"用户点了看看的通知也是 untrusted"同一个理由。
- untrusted 回合可以 `open` / `step` / `wait` / `done` 它自己的事，但不能改动 trusted 的事的 `deliver_to`。否则一条通知就能把你交代的事的结果转寄给别人。
- `TurnGuards` 拒绝 untrusted 回合的 `person merge`。

## 6. 迁移

- **`cares` 的 `promise` → 事。**分界很清楚：**事会结束，在意不会结束**。`place` / `person` / `curiosity` / `habit` 留在 cares。旧的 promise 迁成 `kind=self` 的事，`due` 和 `source` 原样保留；cares 不再接受 `promise`，返回一句话指向 `task`。
- **`People.Owed` → 事。**`i_owe` 迁成 `deliver_to` 指向这个人的事；`they_owe` 迁成 `waiting_on` 等这个人的事。`person` 工具的 `owe` / `settle` 改成转调 `task`，返回里说明已经改了；人的档案（`forPrompt`）里列出和他有关的事，只是一个视图，不再单独存一份。`People.pull` 改为从事里读。
- **`Todo` 保留**，只加一个可选的 `task` 字段。
- **`Unfinished` 不动**，层级不同。
- 迁移在笔记本加载时跑一次，用 meta 标记，和默认 todo 的种子一样。

## 7. 界面

- 小本本「待办」tab 改名「在办」：上半部分是事（状态、在等谁、下一步，可以 ✕ 放弃）；下半部分是定时，即原来的 todo。两个身体都改。
- 动态里加几行事件：接下了 T3、在等 leader、T3 的回答到了、T3 办完了、放弃了 T3 及原因。
- 人的详情里多一栏「和他有关的事」。

## 8. 分期

1. **人**：按会话区分身份、upsert 查重、merge 和撤销。全部在 core，配单测。单独这一步就能止住重复。
2. **来源锚点 + 自动建档**：两个身体各自从通知里取字段，交给 core。
3. **事**：存储、工具、索引行、triage 匹配、心跳逾期、回合结束检查。
4. **迁移和界面**：promise / Owed 迁移，小本本「在办」，动态事件。改 prompt 要重生成 golden 快照。

## 9. 没解决的

- **微信没有稳定 ID。**按会话区分的显示名会因为对方改昵称而失效。这时会建一条新的未确认记录，靠复盘的疑似重复去合。
- **Mac 微信默认不给发送者。**只能锚到会话，锚不到人，交付只能引用回复，不能 @。
- **引用回复依赖找到原消息。**消息被刷走很远时，模型可能要翻很久，或者找不到。那时只能退到按显示名 @。
