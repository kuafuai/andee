# 设计草案：Andee 做 router，dsh 做 worker —— 以及 dsh 里的 Andee 入口

状态：Mac 端第 2–4 节已实现（`desktop/dsh/`，分支 `feat/dsh-worker`）；第 5 节插件、手机经配对派活未做 · 适用：Mac 身体（派活给 dsh）+ 两个身体（经配对，手机也能派）· 2026-11-12

关联：`tasks.zh-CN.md`（事）、`desktop-shell-tool.zh-CN.md`（Mac 的终端是一只手）、`core/peer/`（朋友 / `GuestHost`）、`inner-drive.zh-CN.md`（心跳与主动）

> ✅ 已对照 dsh 0.2.2-rc.1 实测核实（2026-11-12）：SDK 是 `dsh --profile sdk`，按行分帧的 JSON-RPC，流程为 `initialize` → `session/working-directory/set`（或 `session/resume` 续接）→ `session/query` → `session/wait`；**协议没有取消方法**，所以每件活一个进程、取消即结束进程；默认权限预设是 `workspace-write`，写到文件夹外会被沙箱拒绝，越界要走 `approval/request`；sdk profile 不带 `workspace-changes`，所以产出物清单由 Andee 对文件夹做前后快照得到。下文仍标「待核实」的只剩插件相关部分。
>
> ⚠️ 凡标「**待核实**」的，是 dsh 协议或行为细节（SDK 的 JSON-RPC 方法、续接与事件的确切形状、插件清单与上架流程），编码前要对照 dsh 文档或源码落实。下面引用的 dsh 包名都是在本机安装目录（`@deepseek-ai/dsh` 0.2.2-rc.1）里实际看到的。

## 0. 一句话

**Andee 是 router，dsh 的会话是 worker。** Andee 对着人、从很多来源接活、按策略判断、记账、用自己的口吻交付；需要读仓库、调研、跑长命令、批量处理文件这类能并行的通用活，派给 dsh 的会话去做。操作屏幕、摄像头这类只能本机串行做的"身体"活，Andee 自己亲手做——它是 router，也是身体这一种 worker。

另外在 dsh 的插件市场里放一个 Andee 插件做引流：装上以后，dsh 里的请求变成**又一个投给 Andee 的任务来源**，经配对，手机上的 Andee 也能借到电脑那边的手。主导权始终在 Andee。

## 1. 参照：DeepSeek 的 dsh-superagent（router + worker）

DeepSeek Harness 团队开源了 `dsh-superagent-prototype`（0.1.0，研究原型，README 写明"仅供参考、非官方产品"，公开版与内部版不完全一致）。它的结构（`docs/007-architecture.md`）：

- **router（主会话）**：和人说话、执行策略、分诊、派活，**不亲自做工单**（不读代码是提示词规定，不是工具限制）；有 `noWait` 守卫（不许睡眠，shell 超时不超过 30 s，job 等待不超过 5 s），理由是"报告会自动回来，等待只会延误新的候选"。
- **worker（每个工单一个独立会话、独立目录）**：并行，有 `WorkerSlots` 上限；不能找人、不能开别的会话，只读自己工单相关的东西；工单结束后再调用工具会被拒。做完调 `report`，router 收到不超过 600 字的摘要，提问则立即转给 router。
- **工单（Ticket）**：来源（GitHub 轮询、飞书事件）产生触发 → 分给已订阅的工单，或排进主会话评估；Engine 是唯一能改状态的地方；有"等人回复"的状态（`waitsForPerson`）；人在已结束工单的线程里再说话，会**续接**那个工单。
- **策略**：发信人在白名单里且点名了它才放行；主动接活只在 auto 模式下生效，否则只记一条"本来会接"。

**和 Andee 的对照**：router 那一半，Andee 已经各自长出来了——

| superagent | Andee |
|---|---|
| 多来源触发（GitHub、飞书） | 通知、待办、心跳、朋友请求、语音和打字 |
| Ticket + 跟踪的线程 | 「事」（`Tasks`）：来源、在等谁、对方回没回由设备记 |
| 触发分给已订阅的工单 | `NotifyTasks`：通知进来先认出"这是在回答哪件事" |
| 主会话评估候选 | 通知分诊（不带工具的单次调用：act / tell / ignore） |
| 策略：谁说的才放行 | `TurnGuards`、不受信任轮次、守卫段落 |
| 主动只在 auto 模式下生效 | 「自己动起来」开关、心跳的预算 |
| worker 回报 → router 收摘要 | 朋友回报以新轮次叫醒 Andee |
| 等人回复 | 任务的等待、`Wait.seen` |

**不同的地方，也是这份方案要补的：**
1. **Andee 自己就是 worker，而且只有一个循环。** 一个长活在跑，用户的下一句就要排队（`show_html` 曾经卡住对话、`WaitBudget` 的由来，都是这个结构造成的）。把能并行的活交给 dsh worker，主循环才能一直马上回应人。
2. **router 没有自我，Andee 有。** Andee 当 router，是"那个会做决定、亲口回你话的个体"在当，不是一个调度服务。人格、日记、守卫都留在 Andee 这边，dsh worker 不带人格、不直接对用户说话。
3. **信任方向相反。** superagent 里，人跟进时由 worker 决定、router 只能叫停；Andee 里由它自己这一轮决定，worker 交回来的东西都当外部数据。

## 2. Andee 侧：把 dsh 当 worker 用

### 2.1 形态

- 常驻一个 `dsh --profile sdk` 进程（JSON-RPC over stdio，**待核实**），不是每次冷启动 `dsh headless`。常驻才能流式接事件、转审批、随时取消。
- Mac 上新增一个 `ToolProvider`（暂名 `DshProvider`），给模型几个工具：`delegate`（派活）/ `delegate_status` / `delegate_cancel`。手机上没有 dsh，这几个工具不出现（经配对的情况见第 5 节）。
- **一件「事」对应一个 worker 会话**：派活时开一件事（或接着用已有的那件事），挂一个"等 dsh"的等待。

### 2.2 照搬 router 的规矩

- **派了就走，不等**（相当于 superagent 的 `noWait`）：`delegate` 立刻返回；worker 的回报以一个新轮次叫醒 Andee，和 `ask_friend` 一样。Andee 已有的 `WaitBudget` 是同一个思路，这里不会让主循环陷在等待里。
- **回报有长度上限**（参照 600 字）：worker 的结果先由设备截成摘要放进上下文，全文留在产出物里（见第 4 节），需要时再读。这样不撑爆上下文，也和现在的修剪、归档机制一致。
- **worker 的提问马上转上来**：dsh 需要审批或问人时，弹 Andee 自己的卡片（Mac 的 `PromptWindow`），不让 worker 直接找用户。
- ~~点一下球全部停止~~ **点球不停 worker**（实测后改）：交出去的活本来就该在用户继续和 Andee 说话时接着做；起初点球连带取消，结果用户点球想补一句，正在调研的 worker 被砍（2026-11-12）。只有 `delegate_cancel` 停它。
- **结果是外部数据**：worker 可能上过网、读过不可信的文件，它的回报按通知那样隔开，不当成用户说的话。
- **并发上限**（参照 `WorkerSlots`）：同时最多 N 个 worker，超出排队，避免一句话放出一群 agent 花掉用户的钱。

### 2.3 信任随发起这一轮走

- 派不派，由 Andee 自己决定。通知、待办、心跳、朋友请求触发的轮次，只要 Andee 判断该派，就放行（2026-11-12 机主明确：Andee 是设备的灵魂，守卫不替它做决定；第一版曾拒绝通知触发的轮次，已去掉）。
- 唯一保留的限制管的是 worker 能碰什么，不是 Andee 能不能决定：worker 要写工作文件夹以外的地方，只有用户亲口发起的活才会弹卡询问，其他一律拒绝，因为没人可问。
- 静默的整理轮次（凌晨回顾）不能派，那时没人在。
- 主动模式参照 superagent：心跳想派活但没开相应开关时，只记一条"本来会派什么、为什么"，用户可以在时间线里看到，确认后再放行。

## 3. 会话复用：重复的活接着原来的会话

**是的，不该每次都开新会话。** 接着原来的会话，worker 已经读过的仓库结构、做过的决定、用户的偏好都在，更省 token，也更连贯。dsh 原生支持续接（`dsh-session-persistence`；`headless` 带 `--session-id`；SDK 的续接方法**待核实**）。superagent 也是这么做的：人在已结束的工单线程里再说话，就续接那个工单。

**怎么判断续接还是新开（由设备判断，不交给模型）：**

| 情况 | 做法 |
|---|---|
| 同一件「事」继续（追问、返工、"再改一下"） | 续接这件事绑定的会话 |
| 周期性的同类活（每周周报、每天整理下载目录） | 每个周期任务固定一个会话：待办 / cron 的 id → 会话 id |
| 明确的新活、不相干的活 | 新开会话 |
| 拿不准 | 新开（串到别的任务上下文里，比多花一点 token 更糟） |

**几条硬规则：**
- **信任不能混。** 一个由用户亲口要求开出来的会话，不能被不受信任的轮次续接；反过来，由不受信任来源开的会话，也不能在用户的轮次里升级成可写。续接前比对会话的信任等级和这一轮的，不一致就新开。会话绑定记录里存它创建时的信任等级。
- **工作目录跟着会话走。** 续接 = 同一个目录；新开 = 新目录（见第 4 节）。
- **会话要有寿命。** 太久没用（比如超过 30 天）或太大的不再续接，新开时把旧会话最后的摘要作为开场材料带进去。dsh 自己有上下文压缩，但一个会话无限续下去，旧决定会干扰新任务。
- **绑定关系存在 Andee 这边**：「事」的记录里加一个字段（暂名 `Task.worker`：会话 id、目录、信任等级、最后使用时间）。小本本"在办"里能看到这件事交给了哪个 worker、还在不在跑。
- 和 Andee 自己的长期记忆分工：worker 会话记的是"这件活做到哪一步"；"这类活以后怎么做"仍按现有规则，写成小本本里的 `way` 或 wiki，不依赖某个 worker 会话一直活着。

## 4. 产出物：worker 产的文件，Andee 怎么知道、怎么交给用户

### 4.1 让 Andee 知道：以设备记录为准，不信回报正文

dsh 已经提供了这个能力，而且原则和 Andee 一样：

- **`dsh-workspace-changes`**：每一轮结束时发一个 `workspace/changes` 事件，列出改动的文件和行数，来源是 git 工作区快照加文件工具编辑前后的整文件备份（没有 git 时只记文件工具的编辑）。摘要和逐文件对比在会话存活期间可以向宿主索取。
- **显式交付**（`dsh-deliverable-file-references`）：worker 可以显式"交付"某个文件。dsh 的原则是列出的路径"来自记录的改动摘要、成功的文件修改与显式交付，**而非收尾正文**"。

Andee 侧照这个做：**产出物清单由设备从事件里拿，不从 worker 的回报文字里解析。** 回报说"我生成了 report.pdf"，但事件里没有这个文件，就不算。每个文件记下路径、大小、类型、是新建还是修改。（具体的事件字段和索取接口**待核实**。）

### 4.2 每个 worker 一个独立目录

- 参照 superagent 的"每个工单一个目录"：`~/Library/Application Support/Andee/workers/<事的id>/`，或用户指定的仓库目录（改代码的活）。
- 好处：产出物有明确的归属；清理时按目录删；Andee 自己的数据目录不在 worker 能写的范围里（和 `ShellPolicy` 不让沙箱读 Andee 数据目录是同一个考虑）。
- 改的是用户自己的仓库时，产出物通常是一个分支或 PR，交付形式就是链接（superagent 的 `report` 可以绑定 PR）。

### 4.3 交给用户

Andee 收到"活做完了 + 产出物清单"以后，用自己的口吻告诉用户，并按文件类型给入口：

| 产出物 | Mac 上怎么交付 | 手机上（经配对，见第 5 节） |
|---|---|---|
| Markdown / 文本 | 用 Andee 现成的阅读器打开（同 wiki 阅读器），或写成 `show_html` 页面 | 小文件直接传到手机显示 |
| HTML / 图片 / PDF | `show_html` 或系统预览打开 | 小文件传过去；大文件只说"在你 Mac 的某个位置" |
| 代码改动 | 显示改动摘要（文件、行数），给分支或 PR 链接，提供"在 Finder 里显示" | 只给摘要和链接 |
| 一批文件 / 大文件 | "在 Finder 里显示"这个目录 | 说明在哪台电脑、哪个目录 |

- **进入「产物」面板**：现在面板里只有 `show_html` 页面，加一种"文件产物"（指向 worker 目录里的文件，带版本），这样产出物不会只留在一句话里，以后还能找到。同一件事返工产生的新版本，沿用产物面板现有的版本规则（一产物一行、v2、v3）。
- **Andee 能读产出物**：文本类产出物 Andee 可以用只读方式读进来，再总结或回答追问（"报告里第三部分说了什么"）。读取走现有的上下文预算和修剪，不整篇塞进去。
- **产出物是外部数据**：不自动执行 worker 生成的脚本或可执行文件；需要运行时，按现有 shell 规则走审批。

### 4.4 保留和清理

- worker 目录默认保留一段时间（比如 30 天）或直到对应的事被放下；之后清理，产物面板里对应的条目标成"已清理"，不留指向不存在文件的死链接。
- 用户在产物面板里可以手动"另存到…"把文件拿走，拿走的不受清理影响。

## 5. dsh 里的 Andee 插件：引流，也是又一个来源

### 5.1 它是什么

在 dsh 的插件市场里放一个 Andee 插件，**目的是引流**。装上之后：

- dsh 里的请求可以发给这个用户自己的 Andee 去做 dsh 做不了的事：操作手机、看摄像头、手机端的提醒和消息。
- 对 Andee 来说，这只是**又多了一个任务来源**，Andee 该干什么还干什么，turn 循环一行不改。原来是用户直接对 Andee 说，现在多了"用户在 dsh 里说"这一条路。

### 5.2 配对：dsh 就是局域网里的一个"朋友"

- 插件里加配对能力，复用 Andee 现成的朋友机制（`core/peer/`）：`PeerQr` 扫码（地址、一次性码、密钥指纹）、同一网络里 mDNS 加记住的地址（`PeerStore.address`）、签名握手（`PeerProtocol`）。Mac 能配，手机也能配，配对是设备对设备的。
- 配对以后，活是**双向**的，两个方向都用现成的信任规则：
  - **Andee → dsh**（第 2 节，走 `ask_friend` 这条路）：Andee 把能并行的活派给 dsh worker，dsh 做完以一个新轮次回报。**手机上的 Andee 也因此借到了电脑那边的手**：shell、文件、通用 agent 这些手机本身不可能有的能力。手机只接收回报和产出物（第 4.3 节），不执行 dsh 的工具，所以对手机是安全的。
  - **dsh → Andee**（插件把 dsh 里的请求转过来）：按"朋友请求"处理，跑在 `GuestHost` 里：空历史、工具白名单、每个调用都不受信任、不可逆的动作弹卡让主人点允许。手机上对微信的写操作本来就被拦截，从 dsh 来的请求同样拦。
- 前提是有一台开着 dsh 的电脑在同一个网络里，就像 `ask_friend` 要求朋友在线。不在线时如实告诉用户"现在够不着电脑"，不假装能做。跨网络需要中继，目前还没有，先限定在同一网络。

### 5.3 两档

- **A：纯引流。** 插件只展示介绍和下载入口，不连真机。轻、安全、审核快，先用它验证 dsh 市场这条渠道有没有流量。
- **B：引流加配对**（5.2）。说服力更强，因为它真给 dsh 补了"身体"，也给手机补了"电脑的手"。

建议先上 A，第 2 节做完以后上 B。

## 6. 防环与费用

- **不许转包**：从 dsh 来的请求（guest 轮次）不能再派回 dsh；`PEER` 轮次本来就不能 `peer.ask`，这里加同类规则。避免两边把一件活踢来踢去、没人看着花钱。
- **worker 的 token 计入 Andee 的账**：dsh 用的是同一个 DeepSeek key，但用量不经过 Andee 的预算和 trace。每次派活有次数和并发上限，结束后把用量记进时间线（"这件事 dsh 用了约 X token"）。

## 7. 从 superagent 借鉴的东西（有价值、可以直接用）

1. **router 不等待**：派了就走，报告自己回来。Andee 的 `WaitBudget` 可以顺着这个思路，把"盯着别人的长活"整体改成派活加回报。
2. **只有一个地方能写任务状态**：Andee 的 `Tasks` 已经基本做到，接 worker 时保持这一点，worker 的事件只能经过设备去改任务，不能让模型直接改。
3. **对外的动作可靠落盘、失败重试**：Andee 朋友机制已有 30 分钟的 outbox，worker 回报和交付照此处理。
4. **回报有长度上限，全文另存**：参照 600 字。
5. **主动只在开关打开时生效，否则只记"本来会做"**：可以用在心跳上，让用户先看到 Andee 想自己做什么，再决定要不要放开。
6. **worker 不能找人、不能开新会话、只读自己的活**：dsh worker 照此约束，所有对人的接触都经过 Andee。

## 8. 落地清单

**dsh 侧（核实）**
- [ ] SDK profile 的 JSON-RPC：建会话、续接会话、发任务、收事件（含 `workspace/changes` 和交付）、审批请求、取消。
- [ ] 插件怎么写、怎么上架它的市场。
- [ ] dsh 能否作为 MCP 客户端调用外部工具（`dsh-mcp-client`）。如果能，插件 B 也许直接用 MCP 暴露 Andee，省掉自定义协议。

**Andee 侧**
- [ ] `desktop/`：`DshProvider`（常驻 sdk 进程、`delegate` 系列工具、并发上限）。
- [ ] `Tasks`：加 `worker` 字段（会话 id、目录、信任等级、最后使用时间）和续接规则（第 3 节）。
- [ ] 产出物：从 dsh 事件生成清单，产物面板加"文件产物"，worker 目录的保留和清理（第 4 节）。
- [ ] `TurnGuards`：`dsh.delegate` 的信任规则和防转包。
- [ ] 回报：摘要进上下文、全文入产出物、审批转到 Andee 的卡片、`stopAll` 连带取消、用量记入时间线。
- [ ] 插件 A（纯引流）。
- [ ] 插件 B：配对沿用 `PeerQr` / `PeerStore`，请求接到 `PeerTasks` 的 guest 入口。

## 9. 没定的

1. 先做 Mac 上的派活（第 2–4 节），还是先上插件 A 摆摊？（建议并行：A 很轻。）
2. 插件 B 用自定义协议（9008 / hub）还是 MCP？取决于 dsh 能否作为 MCP 客户端。
3. worker 目录放 Andee 自己的数据目录下，还是让用户指定一个工作区？改代码的活显然在用户的仓库里，其他活需要定一个默认位置。
4. 产出物保留多久、默认上限多大。

## 10. 实现与草案的差异（2026-11-12，Mac 端）

- **每件活都挂在「事」上**（`DshTaskLink`）：模型用 `for_task` 点名的那件；没点名就用续接的 worker 正在办的那件；都没有就由设备新开一件（`origin = dsh`）。设备给这件事挂一个 `worker` 等待（模型设不了），回报到达时由设备回答它（`Tasks.workerAnswered`），回报那一轮带上这件事的完整记录。被叫停的活回答为已读，不会被心跳重做；Andee 退出时被打断的活让事变成 ready。worker 自己的索引（`dsh_workers.json`）仍记会话 id、目录、信任等级等，并记下它在办哪件事。
- **不提供跳到 dsh 网页里对应会话的链接**（试过后去掉）：dsh web 会把另一个进程正在跑的会话显示成「任务已停止 … 本轮已中止」；而且它只要显示过某个会话，就会一直占着这个会话的写锁，Andee 续接时就会撞上 `writer-held`。现在的做法是：续接撞锁时，在同一个文件夹里开一个新会话接着做，同时带上旧的回报和文件夹里已有的文件。想看工作者在干什么，看 Andee 自己的进度卡（`DshLive`）：第几步、用时、它自己的清单、最近几个动作。
- **产出物没有进「产物」面板。** 现在的交付方式是：回报里列出设备记录的文件；时间线上的行带「文件夹 ›」，一点就在 Finder 里打开；Andee 用 `read_worker_file` 读文本文件，用 `open_worker_folder` 打开文件夹。第 4.3 节的「文件产物」条目和第 4.4 节的定期清理还没做；文件夹目前一直保留。
- **产出物清单是 Andee 对文件夹做前后快照得到的**，不是 dsh 的 `workspace/changes` 事件：sdk profile 不带这个插件。原则不变：只信设备的记录，不信回报正文。
- **越界审批**：用户亲口交代的活弹 `AskGate` 卡片（允许一次 / 不允许，5 分钟），其他一律拒绝。
- **系统提示词没改。** 什么时候派活，全写在 `delegate_task` 的工具描述里（和 `run_command` 一样），这样没装 dsh 的机器上提示词一个字都不变。
- 并发上限 2，单件活最长 2 小时。
