# v0.6.1

**One codebase, ten packages, and none of them carries a key.** Every variant is built from the same
checkout: Android and macOS, each in Chinese and English. Android splits by CPU and the Mac by chip, so
four builds produce ten files — and each one is verified after building to be the variant its name says
it is.

This release is mostly a fix for how v0.6.0 was packaged. The Mac build shipped with **no server
configured**, and the Mac then fell back to a different backend silently instead of saying so. That is
fixed, along with the two reasons it could happen.

> **These binaries carry no credentials.** No CodeFlying key, no voice-provider key, and no Google key —
> the build writes them empty and refuses a key passed on the command line. **You supply your own**: sign
> up at the link inside the app, then paste the key into **Settings → Backend**. Starting is free and the
> free allowance is finite.
>
> Both servers are HTTPS-only, and each package is built to point at the right one for its language:
> the English packages at `myapp.codeflying.app`, the Chinese at `baas.kuafuai.net`. You do not choose
> this — the package you downloaded already knows.
>
> **The macOS packages are signed with a local identity, not an Apple Developer ID**, so Gatekeeper
> refuses the first launch. On macOS 15 the old "right-click → Open" trick no longer exists; see
> **[Opening the Mac app](#opening-the-mac-app)** below.

## Highlights

- **Every variant from one checkout.** `build_variants.sh` builds all four; nothing is edited by hand
  between them, which was previously how the wrong package got shipped.
- **A "Chinese" Mac package now comes up in Chinese** — it did not before. The Mac had no build-time
  default language, so it read the machine's locale and a Chinese package opened on an English Mac was
  English.
- **A second build no longer silently reuses the first one's configuration.** This is what made the
  first attempt at this release produce **English APKs filed under Chinese names** — see *Fixed*, below.
- **No package can contain a key.** Not "the key happens to be commented out", but "the build cannot
  compile one in and refuses to be told to".

## What's Changed

### Fixed

- **The Mac had no build-time default language.** `DEFAULT_LANG` is now generated into the Mac app's
  config and read by `Strings.lang()`, ranking below a language the user has picked and above the system
  locale — the same rule the phone uses. Without it a package built as Chinese came up English on an
  English machine, which made the name a lie.
- **A second variant build reused the first one's `BuildConfig`.** `-P` values are read during
  configuration, which AGP's up-to-date check for `generateDebugBuildConfig` cannot see, so building
  Chinese and then English produced **English packages under the Chinese names**: the second run rewrote
  the config and re-packaged, but the first run's task had been skipped, leaving whatever APKs were
  already on disk for the copy step to pick up. Both settings are now declared inputs of that task.
  *This was found by reading `DEFAULT_LANG` out of the finished APK. The build log said
  `BUILD SUCCESSFUL` for both runs, and both runs had produced a plausible-looking file.*
- **Credentials can no longer be baked in.** `CODEFLYING_KEY` and `GOOGLE_VOICE_KEY` are compiled as the
  empty string rather than copied from `local.properties`, and both build files **fail** on
  `-PcodeflyingKey=` / `-PgoogleVoiceKey=` instead of ignoring them. The previous arrangement held only
  while nobody uncommented a key to test something — which is not a guarantee, it is a coincidence.
- **The Mac fell back to a different backend without saying so.** With no server configured the Mac
  resolved to the local mode and sent the user's CodeFlying key to `api.deepseek.com`, while the
  self-check reported "Configured" — because it derived the backend from the same fallback. Each package
  now carries its server, so the case does not arise; the silent-fallback shape remains a latent bug and
  is noted under *Known issues*.

### Added

- **`build_variants.sh`** — builds all four variants from one checkout, names the Chinese packages in
  Chinese, moves the runtime image aside between Mac architectures (the trap that yields a mixed bundle
  while reporting success), and checks all four architecture points before accepting a dmg.
- **`verify_variants.py`** — confirms each package is the variant its name claims, by reading the
  **artifact**: the APK's own dex, and `codeflying.properties` from inside the dmg's jar. It checks that
  the server matches the language, the language matches the name, the architecture matches, and that no
  credential is present — including `assets/andee_key.txt`, which the app reads *before* its build
  config and which would therefore override it.

### Changed

- **`-PcodeflyingDomain`, `-PdefaultLang` and `-PcodeflyingSsl`** override `local.properties` on both
  platforms. A variant is stated on the command line, where the build log records it, instead of by
  editing a file and remembering to edit it back.
- **Both servers are HTTPS-only**, measured rather than assumed: `baas.kuafuai.net` answers 200 on https
  and 404 on http; `myapp.codeflying.app` answers 200 on https and does not connect at all on http. So
  `codeflyingSsl=true` is part of the variant.

**Android** (Android 11 / API 30 or later). The APK is per-CPU; pick the one for your device:

### Opening the Mac app

The `.dmg`s are signed with a local identity, not an Apple Developer ID, so Gatekeeper refuses the first
launch of a downloaded copy.

⚠️ **On macOS 15 (Sequoia) and later, "right-click → Open" no longer works** — Apple removed that
override. Most advice online still recommends it. The current route:

1. Double-click the app. It will be refused. Dismiss the dialog.
2. Open **System Settings → Privacy & Security** and scroll to **Security**.
3. There is a line naming Andee as blocked, with an **Open Anyway** button beside it.
4. Confirm, and authenticate.

That button **only appears for about an hour** after the failed launch. If it is missing, launch the app
again and go straight back to Settings.

One more thing worth knowing: the app **inside** the mounted dmg carries no quarantine flag, so it may
launch straight from the dmg — and then be blocked once you drag it to Applications, which does attach
one. Both behaviours are normal; they are not a sign of a damaged download.

### What you supply

No package has a key. After installing, open **Settings → Backend** and either paste a CodeFlying key
(sign up from the link in that panel) or switch to **on-device** and give it an OpenAI-compatible
endpoint and model. A voice key is optional — without one the assistant is silent but still works on
screen.

> **Would you rather not configure keys at all?** Use the one-click page instead —
> **[codeflying.app/andee](https://www.codeflying.app/andee)**, or
> **[codeflying.net/andee](https://www.codeflying.net/andee)** in mainland China. Describe what you want,
> tap the build button, and you get a package with the **tokens already configured** plus a QR code to
> scan. Starting is free and the free token allowance is **finite — once it runs out, tokens must be
> bought.** It is a separate service with no direct relationship to this project, with its own terms,
> pricing and data handling. Note it produces **an Android APK, not a Mac app** — macOS packages can
> only be built on macOS.

## Known issues

- **The Mac still falls back silently when no server is configured.** Each package here carries one, so
  it does not arise for these downloads — but a locally built app with an empty domain still resolves to
  the local backend and sends whatever key it has to `api.deepseek.com`, while the self-check says
  "Configured". The fix would be to make the Mac behave like the phone, which has nowhere to send and
  says so; it is not in this release.
- **Nothing verifies that a key is accepted by the server it is sent to.** These packages are checked for
  the right server and the absence of credentials; whether a given CodeFlying key works against
  `baas.kuafuai.net` versus `myapp.codeflying.app` has not been exercised end-to-end.
- **The Mac build is signed with a local identity, so Gatekeeper refuses the first launch**, and there is
  no notarization. The Settings route above is the only way through it on macOS 15.
- **A Mac build made on another machine without its signing keychain is ad-hoc signed** — its identity
  locks to the build hash, so installing it over an existing copy makes macOS treat it as a **different
  app**: Accessibility and Screen Recording must be granted again. User data is unaffected; it lives in
  `~/Library/Application Support/Andee`.
- **The wake threshold's margin is thin**, carried from `v0.3.2`: the eight measured judgements sit in
  1.47–2.05 with the line landing in the gap between 1.69 and 1.77 — 0.08 wide.
- **A light generated page still fades in over a dark stage.** Carried over from `v0.3.1`; the app's own
  default has been light since `v0.4.1`.
- **`assets/andee_key.txt` is tracked by git and is not in `.gitignore`.** It ships with a single newline,
  which reads as empty. A key written into it would outrank every build setting.
- The two issues `v0.1.0` listed are **unchanged and untouched in this release**:
  `tools/verify_faces_lab.py` still reports 7/16 assertions passing, and the debug WebSocket server
  (`net/BodyWsServer`) still binds `0.0.0.0:9008` with no authentication (documented in `SECURITY.md`).

## Before you install

Read **[DISCLAIMER.md](../../DISCLAIMER.md)** and
**[docs/acceptable-use.md](../acceptable-use.md)** first. On Android the app asks for accessibility,
overlay, notification access, SMS and call log, and it can complete a payment by tapping; on the Mac it
asks for accessibility, screen recording and notifications. The only guardrail on that path is Android's
`FLAG_SECURE`; the prompt-level checks on risky actions are instructions to the model, not enforcement.

## Install from source

```bash
git clone https://github.com/kuafuai/andee
cd andee
git checkout v0.6.1

# one variant, by hand:
./gradlew :app:assembleDebug -PdefaultLang=en -PcodeflyingDomain=myapp.codeflying.app -PcodeflyingSsl=true

# or all four, the way the release was built:
bash ~/.workbuddy/skills/andee-release-ship/scripts/build_variants.sh
```

`-PcodeflyingKey=` and `-PgoogleVoiceKey=` are refused on purpose — a published package carries no
credential.

**Upgrading from v0.6.0:** `versionCode` moves `13 → 14`, so the Android package installs normally. The
Mac app never had a `DEFAULT_LANG` before, so an existing install keeps whatever language the user
picked and falls back to the system locale as it always did — the new default only decides what a fresh
install shows. If you were relying on the Mac's old silent fallback to a local backend, note that these
packages now carry a server, so a fresh install talks to CodeFlying.
